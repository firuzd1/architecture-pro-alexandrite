# Выбор и настройка мониторинга в системе

## Мотивация

Сейчас компания не видит что происходит внутри системы. Проблемы с заказами обнаруживаются только когда клиент звонит и жалуется. К этому моменту заказ уже потерян или задержан на несколько дней.

Мониторинг даст компании:
- Возможность узнать о проблеме раньше клиента
- Понять под какой нагрузкой работает система прямо сейчас
- Обосновать когда нужно масштабировать инфраструктуру
- Снизить время на разбор инцидентов с часов до минут
- Данные для переговоров с бизнесом — сколько заказов потеряно, где узкое место

Без мониторинга компания продолжит терять B2B контракты и клиентов онлайн-магазина.

## Выбор подхода к мониторингу

Для разных частей системы используем разные подходы:

**RED (Rate, Errors, Duration)** — для всех трёх API (онлайн-магазин, CRM, MES). Это сервисы которые обрабатывают запросы пользователей. RED даёт прямой ответ на вопрос "хорошо ли работает сервис с точки зрения пользователя".

**USE (Utilization, Saturation, Errors)** — для инфраструктуры: EC2 инстансы, базы данных, RabbitMQ. Нужно понимать насколько загружены ресурсы и когда они начнут отказывать.

**Четыре золотых сигнала** — для RabbitMQ и очередей сообщений. Здесь важны latency (как быстро обрабатываются сообщения), traffic (сколько сообщений в очереди), errors (dead-letter) и saturation (переполнение очереди).

## Метрики для отслеживания

### RabbitMQ

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| Number of dead-letter-exchange letters | главная метрика потери заказов — если растёт, значит сообщения не обрабатываются | queue_name |
| Number of messages in flight | показывает текущую нагрузку на очередь, помогает выявить узкие места | queue_name |

### Онлайн-магазин API

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| Number of requests (RPS) | базовая метрика нагрузки | endpoint, method |
| Number of requests per user | выявление аномальной активности, защита от DDoS | user_id |
| Response time (latency) | качество работы сервиса с точки зрения клиента | endpoint, percentile |
| Number of HTTP 200 | успешные запросы | endpoint |
| Number of HTTP 500 | ошибки сервера — критично для заказов | endpoint |
| CPU % | утилизация ресурсов | - |
| Memory Utilisation | утилизация памяти | - |
| Number of simultaneous sessions | текущая нагрузка | - |

### CRM API

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| Number of requests (RPS) | нагрузка на CRM | endpoint, method |
| Response time (latency) | скорость работы менеджеров зависит от этого | endpoint |
| Number of HTTP 500 | ошибки при обработке заказов | endpoint |
| CPU % | утилизация | - |
| Memory Utilisation | утилизация | - |

### MES API

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| Number of requests (RPS) | нагрузка на MES | endpoint, method |
| Number of requests per user | операторы могут создавать аномальную нагрузку | user_id |
| Response time (latency) | операторы жалуются на медленную загрузку — это ключевая метрика | endpoint, percentile |
| Number of HTTP 500 | ошибки в производственной системе | endpoint |
| CPU % | утилизация | - |
| Memory Utilisation | утилизация | - |
| Number of simultaneous sessions | сколько операторов работает одновременно | - |

## Насыщенность — пороговые значения

| Ресурс | Порог | Действие |
|--------|-------|----------|
| CPU любого сервиса > 80% | насыщение | добавить инстанс, завести тикет на масштабирование |
| Memory > 85% | насыщение | добавить память или инстанс |
| Dead-letter-queue > 0 | критично | немедленный алерт в Slack, дежурный разбирает причину |
| Messages in flight > 1000 | насыщение | алерт, проверить консьюмеры |
| DB connections > 80% от максимума | насыщение | добавить connection pool или read replica |
| Response time p95 > 3 сек | насыщение | алерт, разбор причины |
