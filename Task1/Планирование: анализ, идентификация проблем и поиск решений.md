# Планирование: анализ, идентификация проблем и поиск решений

## Выявленные проблемы

### Технические проблемы

1. **Медленная загрузка дашборда MES** — операторы жалуются на долгую загрузку первой страницы со списком заказов. Фильтрация и пагинация не помогли. Скорее всего проблема в отсутствии индексов или в том что запрос тянет слишком много данных из БД.

2. **Потеря заказов** — заказы зависают или теряются между системами. Основная причина — сообщения в RabbitMQ могут теряться без должного мониторинга и обработки ошибок. Нет dead-letter-queue для обработки упавших сообщений.

3. **Один инстанс каждого приложения** — нет горизонтального масштабирования. При росте нагрузки система не справляется. Если инстанс падает — сервис недоступен.

4. **Одна БД на запись и чтение** — при росте нагрузки база становится узким местом. Тяжёлые запросы на чтение (дашборд) конкурируют с записью.

5. **Нет мониторинга и трейсинга** — невозможно понять где именно теряется заказ, какой сервис тормозит. Проблемы разбираются со слов клиентов.

6. **Нет кеширования** — список заказов в MES запрашивается из БД при каждом обращении, хотя данные меняются не так часто.

7. **Долгий расчёт стоимости** — MES считает стоимость 2-30 минут. Клиент ждёт ответа синхронно, это блокирует UX.

8. **Ручной деплой в release и prod** — замедляет выпуск фиксов, особенно критично когда нужно срочно починить баг с заказами.

9. **QA только ручное** — один QA инженер не справляется с растущим объёмом тестирования. Релизы задерживаются.

10. **Нет rate limiting на API** — после открытия B2B API система была завалена заказами без какого-либо ограничения нагрузки.

### Бизнес-проблемы

1. Клиенты не получают заказы вовремя — репутационный ущерб
2. Потеря крупных B2B контрактов из-за технических проблем
3. Операторы не могут нормально работать — снижение производительности
4. Невозможно масштабировать бизнес при текущей архитектуре

## Инициативы для устранения проблем

1. Настроить мониторинг и алертинг (RabbitMQ, API, БД)
2. Внедрить трейсинг заказов через все системы
3. Добавить dead-letter-queue в RabbitMQ с алертами
4. Оптимизировать запросы дашборда MES — индексы, кеширование
5. Внедрить кеширование списка заказов через Redis
6. Добавить rate limiting на B2B API
7. Перевести приложения в Kubernetes для горизонтального масштабирования
8. Настроить репликацию БД (read replica для тяжёлых запросов)
9. Сделать расчёт стоимости асинхронным с уведомлением клиента
10. Автоматизировать деплой в release окружение
11. Внедрить автотесты — помочь QA инженеру с автоматизацией
12. Настроить централизованное логирование

## Приоритизация инициатив

### Топ-3 на ближайшие полгода

**1. Мониторинг + dead-letter-queue в RabbitMQ**
Это самое критичное прямо сейчас. Без мониторинга мы вслепую. Dead-letter-queue остановит потерю заказов. Реализуется за 1-2 недели, даёт немедленный эффект.

**2. Кеширование и оптимизация дашборда MES**
Операторы не могут нормально работать — это блокирует производство. Кеш списка заказов через Redis и правильные индексы в БД решат проблему за 2-3 недели.

**3. Трейсинг заказов**
Позволит видеть где именно теряется заказ и быстро реагировать. После мониторинга это второй по важности инструмент для команды.

## Целевая архитектура через полгода

- Все три приложения задеплоены в Kubernetes с горизонтальным масштабированием
- Redis кеш для MES дашборда
- Централизованный мониторинг (Prometheus + Grafana)
- Трейсинг через OpenTelemetry + Jaeger
- Централизованное логирование (ELK или OpenSearch)
- Dead-letter-queue в RabbitMQ с алертами
- Read replica для БД MES
- Rate limiting на B2B API
- Асинхронный расчёт стоимости с уведомлением клиента
- Автоматический деплой в release окружение
