# Архитектурное решение по трейсингу

## Системы которые нужно покрыть трейсингом

Заказ проходит через несколько систем и может зависнуть в любой из них:

1. **Онлайн-магазин** — создание заказа, загрузка 3D-модели, отправка в MES
2. **RabbitMQ** — передача сообщений между системами, здесь чаще всего теряются заказы
3. **MES** — расчёт стоимости (2-30 минут), изменение статусов заказа
4. **CRM** — подтверждение заказа, закрытие заказа

## Список данных для трейсинга

- trace_id — уникальный идентификатор трейса для всей цепочки обработки заказа
- span_id — идентификатор конкретного шага
- order_id — номер заказа (обязательно во всех спанах)
- user_id — идентификатор клиента
- service_name — название сервиса (shop, crm, mes)
- timestamp — время начала и конца операции
- duration — длительность операции
- status — успех или ошибка
- error_message — сообщение об ошибке если есть
- http_method, http_url — для REST вызовов
- queue_name — для RabbitMQ сообщений
- order_status — статус заказа в момент операции

## Мотивация

Сейчас команда не знает где именно теряется заказ. Когда клиент звонит с жалобой, разработчик тратит часы на ручной поиск по логам нескольких систем.

Трейсинг даст компании:
- Видеть полный путь заказа от создания до доставки в одном интерфейсе
- Находить узкое место за минуты а не часы
- Понять почему расчёт стоимости занимает 30 минут у конкретного заказа
- Видеть где именно потерялось сообщение в RabbitMQ

Технические и бизнес-метрики после внедрения:
1. Время разбора инцидента с заказом — с нескольких часов до 15 минут
2. Количество потерянных заказов — должно снизиться на 80%
3. MTTR (среднее время восстановления) — снижение в 3-5 раз
4. Удовлетворённость операторов — меньше времени на ручной поиск проблем
5. Количество жалоб от B2B клиентов — снижение за счёт быстрого реагирования

## Предлагаемое решение

Используем **OpenTelemetry** как стандарт инструментирования + **Jaeger** как бэкенд для хранения и визуализации трейсов.

Почему OpenTelemetry + Jaeger:
- OpenTelemetry — открытый стандарт, поддерживается Java, C# и Vue
- Jaeger — бесплатный, простой в развёртывании, хорошо интегрируется с OpenTelemetry
- Команда уже использует Yandex Cloud, можно задеплоить Jaeger как контейнер

Компоненты которые нужно добавить:
- OpenTelemetry SDK в онлайн-магазин (Java Spring Boot)
- OpenTelemetry SDK в CRM (Java Spring Boot)
- OpenTelemetry SDK в MES (C#)
- OpenTelemetry Collector — агрегирует трейсы и отправляет в Jaeger
- Jaeger — хранение и визуализация трейсов
- Инструментирование RabbitMQ — передача trace_id через headers сообщений

Для RabbitMQ нужно добавить propagation контекста через message headers чтобы трейс не обрывался при передаче сообщения.

Ссылка на диаграмму: [containers-with-tracing.puml](containers-with-tracing.puml)

## Компромиссы

- MES написан на C# — нужна отдельная реализация от Java сервисов, но OpenTelemetry хорошо поддерживает оба языка
- Расчёт стоимости может занимать 30 минут — трейс будет "висеть" всё это время, нужно настроить большой timeout в Jaeger
- Добавление трейсинга увеличивает latency каждого запроса на 1-5мс — незначительно
- Хранение трейсов требует дополнительного места — нужно настроить TTL на 30 дней

## Безопасность

- Jaeger UI доступен только внутри корпоративной сети, не публичный
- Аутентификация в Jaeger через корпоративный SSO — доступ только для разработчиков и поддержки
- В трейсы не попадают персональные данные клиентов (email, телефон) — только order_id и user_id
- Логи трейсов хранятся не более 30 дней
