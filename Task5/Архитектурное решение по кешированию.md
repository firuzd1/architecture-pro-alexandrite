# Архитектурное решение по кешированию

## Мотивация

Операторы жалуются на медленную загрузку дашборда MES со списком заказов. Фильтрация и пагинация не помогли. Проблема в том что при каждом обращении к дашборду система делает тяжёлый запрос к БД — выбирает все активные заказы с фильтрацией по статусам.

При этом список заказов меняется не так часто — статус заказа меняется несколько раз в день, а операторы обновляют страницу постоянно.

Кеширование поможет:
- Убрать повторные тяжёлые запросы к БД
- Ускорить загрузку дашборда с нескольких секунд до миллисекунд
- Снизить нагрузку на БД MES
- Дать операторам нормально работать и брать заказы быстрее

Элементы системы для кеширования:
- Список заказов по статусам в MES (основная проблема)
- Данные о заказе при просмотре деталей

## Предлагаемое решение

### Тип кеширования — серверное

Клиентское кеширование (в браузере) не подойдёт — операторам нужны актуальные данные о заказах, иначе два оператора возьмут один и тот же заказ.

Серверное кеширование через **Redis** — данные кешируются на сервере и все операторы видят одинаковый актуальный список.

### Паттерн — Cache-Aside

При чтении:
1. MES бэкенд проверяет Redis
2. Если данные есть (cache hit) — возвращает из кеша
3. Если данных нет (cache miss) — запрашивает БД, сохраняет в Redis, возвращает клиенту

При изменении статуса заказа:
1. MES обновляет статус в БД
2. MES инвалидирует кеш для затронутых ключей

Почему Cache-Aside а не другие паттерны:

| Паттерн | Подходит? | Причина |
|---------|-----------|---------|
| Cache-Aside | +         | простой, гибкий, инвалидация при изменении |
| Write-Through | нет       | обновляет кеш при каждой записи — лишняя нагрузка при частых изменениях статусов |
| Refresh-Ahead | нет       | сложнее в реализации, нет чёткого понимания когда данные устареют |

### Стратегия инвалидации — программная по ключу

При изменении статуса заказа MES явно удаляет из Redis ключи с кешем списков заказов затронутых статусов.

Например при смене статуса с `PRICE_CALCULATED` на `MANUFACTURING_APPROVED`:
- удаляем ключ `orders:status:PRICE_CALCULATED`
- удаляем ключ `orders:status:MANUFACTURING_APPROVED`

Дополнительно TTL 5 минут на все ключи — страховка на случай если инвалидация не сработала.

| Стратегия | Подходит? | Причина |
|----------|-----------|---------|
| Программная по ключу | +         | точная инвалидация только нужных ключей при изменении статуса |
| Временная (только TTL) | частично  | данные могут быть устаревшими до 5 минут — операторы увидят неактуальный список |
| Полная очистка кеша | нет       | при каждом изменении очищаем весь кеш — теряем все преимущества |
